#+TITLE: Roadmap

* SCHEDULER
*** ABSTRACT
**** Scheduler Design Goals

I want each worker thread managed by the scheduler to represent a CPU core. Each core has its own unique ID, its own run queue, and can be brought online or shut down independently. Every core executes an infinite scheduling loop, continuously selecting and executing tasks. A task may either complete normally or run indefinitely, mirroring how a real operating system schedules threads.

Tasks should be prioritized, although the exact scheduling policy is still to be determined. Since the user cannot accurately predict a task's execution time beforehand, the scheduler should include a runtime predictor. Whenever a task completes, its measured execution time should be fed back into the predictor so that future instances of the same task can be scheduled more intelligently.

An infinitely running task is currently considered valid behavior. Such a task simply occupies its assigned core until it finishes (if ever). This limitation is accepted in the initial design.

*Future work (not part of the initial implementation):* introduce cooperative multitasking through a =task_yield()= primitive. A task that contains a loop which may never terminate would be expected to periodically call =task_yield()=. This function would save the task's execution context, place the task back into the run queue, and allow the scheduler to execute other tasks before later resuming it. Whether this feature is implemented, and how the execution context is represented, is intentionally left for a future revision.

Tasks may also create sub-tasks, similarly to a process performing a =fork()=. This will likely be exposed through an API such as =task_fork()= and =task_exec()=, although the exact interface remains to be designed.

Tasks should be migratable between cores. If a core is shut down, all runnable tasks assigned to it must be migrated to another online core before the worker thread exits. Additionally, cores should eventually be able to balance load automatically: an underutilized core may request work from other cores, while an overloaded core may choose to migrate tasks to reduce its workload. The precise migration policy is still an open design question.

The scheduler distinguishes between the bootstrap core and worker cores. The bootstrap core executes on the thread that creates the scheduler, while all remaining cores execute on dedicated worker threads. The scheduler topology is fixed when the scheduler is created; adding or removing cores at runtime (CPU hot-plugging) is intentionally out of scope for the initial implementation.

*** ROADMAP
**** Phase 0 - Core Architecture

=Goal:= Build the scheduler skeleton.

- *Components* ::
  * =idsched_t=
  * =idsched_core_t=
  * =idsched_task_t=
  * Core run queue
  * Scheduler creation/destruction
  * Bootstrap core (Core 0)
  * Worker cores

- *Invariants* ::
  * Number of cores is fixed at creation.
  * Core 0 runs on the creator thread.
  * Every other core owns one pthread.
  * Every core has exactly one run queue.
  * Every task belongs to exactly one scheduler.

**** Phase 1 - Basic Task Execution

=Goal:= Execute tasks concurrently

- *Features* ::
  * Task creation
  * Submit task
  * =READY= / =RUNNING= / =DONE= states
  * Worker loop
  * Graceful scheduler shutdown

- *Invariants* ::
  * Every =READY= task is inside exactly one run queue.
  * Every =RUNNING= task belongs to exactly one core.
  * A task instance executes at most once.
  * No migration.
  * No priorities.

The phase ends when multiple cores can execute independent tasks correctly.

**** Phase 2 - Priority Scheduling

=Goal:= Replace FIFO scheduling.

- *Features* ::
  * Priority queue
  * Runtime predictor
  * Global runtime predictor
  * Per-core local runtime predictors
  * EMA execution predictor
  * Priority comparator

- *Invariants* ::
  * Priority is computed when a task becomes =READY=.
  * Predictor updates only affect future tasks instances.
  * Existing =READY= task instances never change priority.
  * Every completed task updates both the local predictor of the executing core and the scheduler's global predictor.
  * When predicting a task's runtime, the scheduler prefers the local predictor if sufficient history exists; otherwise it falls back to the global predictor.

This makes it not a dynamic scheduler.
The exact policy for combining local and global predictions is intentionally left unspecified and may evolve.

**** Phase 3 - Dynamic Task Graph

=Goal:= Running tasks can create, replace, and synchronize on execution contexts through a syscall trap model.

- *Features* ::
  * Scheduler space kernel stack (=shctx=) and syscall trap dispatch (=i_schedcall= / =i_dispatch_schedcall=), used by everything below.
  * =task_yield()=, cooperative preemption point.
  * =task_fork()=, full stack duplication with pointer relocation.
  * =task_exec()=, in place context replacement.
  * =task_wait()= / =task_waittask()=, parent/child exit synchronization.
  * Orphan reparenting to the background reaper, with automatic cleanup for reaper owned tasks.

- *Invariants* ::
  * Children belong to the same scheduler as their parent.
  * =task_fork()= duplicates the parent's user context (=ctx=) and scheduler space context (=shctx=), copying both stacks and relocating any pointer that referenced the parent's stack or the parent task struct.
  * Parent and child resume at the same instruction, on independent, non overlapping stacks.
  * Parent's fork call returns the child's task pointer, child's fork call returns 0/NULL, surfaced through =sc_ret=.
  * =task_fork()= leaves the parent unchanged on allocation failure. No partial child, no queue mutation. Reports failure via =IDSCHED_INVALID_CHILD=.
  * =task_exec()= replaces only the entry point/context; tid, =prnt=, =children=, =sibling=, and any task blocked waiting on this one are preserved.
  * Child starts =READY= unless blocked on parent/child exit sync (=wait_chldexit=). That's the only dependency this phase implements.
  * Parent continues executing after =task_fork()=.
  * A task blocked in =wait()= / =wait4()= goes back to =READY= exactly once when the awaited condition is satisfied, and never blocks if the condition already holds.
  * Every wait/exit syscall sets an explicit outcome (=ISC_WECHILD= / =ISC_WNOWAIT= / =ISC_WREAPED=) and an explicit =sc_ret= on every return path.
  * Idle is excluded from the run queue and from every fork/exec/wait path by identity, not by flag state.
  * A task created via =idsched_task_create()= is user owned (=IDSCHED_TASK_USROWN=) and never auto freed by the reaper. A task created via =task_fork()= is reaper owned and gets freed once reaped or adopted as an orphan.
  * An orphaned task is reparented to the scheduler's reaper.

- *Dropped* ::
  * Generic task to task dependency graphs. Not doing this anymore, keeping it to parent/child exit sync only.

- *Known limitations* ::
  * Stack relocation on fork (=i_relocate_stack= / =i_fix_frame_chain=) is a best effort pointer scan, not COW. x86-64 only, assumes frame pointer based stacks.

**** Phase 4 - Core Management

=Goal:= Treat cores like CPUs.

- *Features* ::
  * Core shutdown / startup / states.
  * Bootstrap core management.
  * ACPI watcher thread.
  * Signal driven bootstrap shutdown.

- *Invariants* ::
  * Shutting down a core never loses tasks.
  * The currently running task finishes before the core shuts down.
  * =READY= tasks are migrated before the worker thread exits.
  * No hot plugging.
  * Core 0 can only be shut down via signaling the ACPI.

**** Phase 5 - Task Migration

=Goal:= Move work between cores.

- *Features* ::
  * Manual migration.
  * Automatic migration.
  * Load requests / load donation.

- *Policy (initial)* ::
  * Only =READY= task instances may migrate.

- *Future policies* ::
  * Work stealing, load balancing, migration heuristics.

**** Phase 6 - Scheduler Classes

=Goal:= Replace the single hardcoded priority policy with a layered class system. Each core picks a task by walking classes in a fixed order (e.g. stop, deadline, realtime, fair, idle). Idle stays structurally excluded, same as Phase 3, it's never a candidate in a queue, only the fallback when nothing else is runnable.

- *Features* ::
  * =sched_class= vtable: =pick_next=, =enqueue=, =dequeue=, =task_tick= (for later preemption work).
  * Current EMA priority logic moves into a =fair= class, unchanged in behavior.
  * Idle becomes its own class whose =pick_next= always returns =core->idle= and whose =enqueue= is a no op. Makes the "idle never enters =rq=" rule enforced by the class itself instead of the identity check in =i__schedule=.
  * Room for more classes later (deadline/EDF, etc).

- *DP based batch ordering, possible fair class refinement* ::
  EMA priority sort is greedy. Once a batch of tasks are =READY= at the same time, worth trying:
  * Weighted scheduling to minimize total weighted completion time, using =pred= as processing time and a per task weight (Smith's rule / DP).
  * Job sequencing with deadlines, the standard DP, if/when a deadline field gets added. Maximizes on time completions instead of just shortest predicted job first.
  * Lives as an alternate =pick_next= inside the fair class, operating only on the current =rq= batch, not a persistent graph.
  * If this grows into something bigger, split it into its own module like =HASHMAP= is, instead of baking it into the scheduler. Worth deciding once the class framework actually exists.

- *Invariants* ::
  * Class order is fixed and checked top to bottom on every pick.
  * A class returning nothing from =pick_next= means fall through to the next class, never return idle directly. Only the idle class does that.
  * Adding a class doesn't change existing classes' observable behavior.

**** Phase 7 - Preemption

=Goal:= Stop infinite tasks from monopolizing a core without relying on =task_yield()=.

Not timer only. Options:
- Cross core signal: a core sends a real time signal to a worker when it decides that worker's current task should give way (e.g. a higher priority task just became =READY= there).
- Wakeup driven: extend =i_waitqwakeone= so a wakeup doesn't just mark a task =READY=, it also checks if it should preempt =core->currt= right there, same idea as CFS's =check_preempt_curr= on every wakeup instead of only on a tick.
- perf counter based: fire after N instructions/branches instead of wall clock time, gives reproducible preemption points for testing.
- Compiler inserted safe points, checked opportunistically at function entry/loop back edges.

Given the wakeup machinery already built in Phase 3, wakeup driven preemption is probably the most natural one to build first.

- *Features* ::
  * Preemption trigger (pick one or more of the above).
  * Preemption safe points.

- *Invariants* ::
  * Preemption never interrupts an in progress syscall trap.
  * Scheduler never preempts while executing in scheduler space (=shctx=).

**** Phase 8 - Future Research

*COMPLETELY OPTIONAL*

- *Examples* ::
  * Timer based preemption.
  * Custom assembly context switching.
  * NUMA awareness.
  * CPU affinity.
  * Heterogeneous scheduling.
  * Hot plugging.
  * Multiple schedulers communicating.
  * Revisit dependency graphs as a userspace layer if it turns out I actually need them.

*** RULES
These are frozen unless there is a correctness issue.
1. Every phase must compile before the next begins.
2. Never implement a feature belonging to a later phase.
3. No optimization before correctness within a phase.
4. Each phase has clear invariants that must never be violated.
5. If a new idea appears; it is assigned to the earliest phase it naturally belongs to (or to Phase 8 if it is purely experimental).


*** Notes:
**** Basic tasks priorities
Tasks are ordered by increasing predicted runtime.

If two READY tasks have identical predicted runtimes, they are ordered by
their creation sequence number (tid) so scheduling remains deterministic.

Priority is computed exactly once when a task transitions into READY and
never changes afterwards.

* HASHMAP
*** ABSTRACT
The hashmap library is a high-performance, generic associative container implemented as a single-header library targeting the ISO C99 standard. It is intended as a reusable building block for systems programming, emphasizing portability, predictable performance, and a compact public interface. The implementation follows the STB-style single-header philosophy, allowing the library to be integrated into projects with minimal configuration while remaining fully self-contained.

The library implements a Swiss Table hash map using open addressing, cache-friendly probing, power-of-two capacities, and an 87.5% maximum load factor to maximize lookup and insertion performance while minimizing memory overhead. The implementation is designed to provide excellent average-case performance while maintaining predictable behavior under typical workloads.

Keys and values are stored as opaque pointers without ownership, allowing applications to retain full control over object lifetime and memory management. Arbitrary key types are supported through user-defined hashing and comparison callbacks, while optimized built-in helpers are provided for common key types such as integers, pointers, C strings, and arbitrary byte sequences.

To accommodate a wide variety of applications, memory management is abstracted through a configurable allocator vtable, enabling seamless integration with custom allocators, memory pools, arenas, and debugging allocators without affecting the public interface. The library remains fully functional on any conforming C99 implementation while transparently enabling SIMD-accelerated probing through compile-time feature detection on supported architectures. These optimizations remain entirely internal, preserving identical semantics regardless of the selected backend.

The public API follows a POSIX-inspired design, relying on macro-defined flags and optional variadic arguments to extend function behavior while keeping common operations concise. Compile-time configuration is performed exclusively through preprocessor macros, allowing applications to tailor the library to their requirements without introducing unnecessary runtime abstraction. Invalid combinations of flags or required options constitute invalid API usage and are the responsibility of the caller.

The library intentionally favors explicit caller responsibility over defensive runtime validation, prioritizing efficiency, flexibility, and composability. By exposing a minimal yet extensible interface while hiding implementation details, it provides a robust foundation for high-performance software and serves as a consistent component within a broader family of reusable C containers.
